pl-jobs-lora

A QLoRA fine-tune of a small Polish LLM that turns Polish IT job-posting prose into structured JSON — compared honestly against zero-shot and few-shot API baselines on accuracy, cost, and latency.

Status: in progress

The full pipeline is built and tested — the extraction contract, the prose→JSON dataset (leakage-guarded and split by publication date), the triangulated labeling-QA loop, the shared evaluation harness, and the QLoRA trainer. What remains is the execution: the paid API baseline and the fine-tune on a Colab GPU, which populate the table below. The evaluation figures are therefore shown as an empty shape rather than invented values.

Method

  • An own dataset, not an off-the-shelf one. The training data is built from the sibling project it-job-radar. The input is the posting prose; the labels are triangulated from the platform's structured fields, an LLM reading only the prose, and human adjudication of the disagreements.
  • An apples-to-apples comparison. Zero-shot API, few-shot API, the untuned base, and the QLoRA model are all scored by one pure harness on one frozen test set, per field.
  • Cost as a first-class axis. The report answers the practical question — per one thousand postings, an API at some price versus a fine-tuned model at approximately zero, and at what accuracy.
  • A base model chosen from data. Bielik-1.5B versus Qwen2.5-1.5B was decided by an empirical probe: on a 23-posting development slice, Bielik-1.5B few-shot led on JSON validity and field accuracy (0.91 valid, 0.32 field F1). Zero-shot Bielik emitting no valid JSON is precisely the gap the fine-tune is meant to close.

Data and ethics

Raw postings are never committed: prose is captured at collection time, the processed dataset is frozen on the Hugging Face Hub, and only prose-derived fields leave the machine. Personal data is dropped, and collection is a bounded, throttled sample rather than the whole base. Attribution: theprotocol.it, reused via it-job-radar.
